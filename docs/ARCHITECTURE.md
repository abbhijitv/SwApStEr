# CampusSwap AI architecture

The Next.js client sends buyer preferences to FastAPI once, then retains only a public session response. It never receives the seller's minimum or a buyer's saved maximum in ordinary read responses. A student necessarily knows the preferences they just entered; browser developer tools can inspect that student's own form request.

Each `/advance` runs one independent agent turn. The buyer context contains its own preferences, the public listing, and up to four public messages. The seller context contains its own listing constraints, the public listing, and up to four public messages. Neither context contains the other student's private price limits. Shared offers include voluntarily disclosed price, pickup, duration, and location. Agents communicate through these persisted, structured public offers.

The provider interface is `decide(context: dict) -> Action`. The mock provider computes offers from its own student's values and prior public offers. Ollama receives separate requests for the two roles. One inference lock serializes requests to the same Qwen model; 2,048 context tokens, 220 output tokens, temperature 0, a five-minute keepalive, a 90-second request timeout, and at most two JSON attempts keep local inference bounded.

Agent actions have no free-text field. Public prose is rendered from validated actions and terms, so a model cannot accidentally print a private prompt or price limit into its public message. The model makes the negotiation decisions; the application formats their display. This is intentional selective sharing, not an LLM simulating both students in one prompt.

The coordinator can access both private records to enforce rules. It checks each proposed action against the acting student's constraints. Acceptance must equal the existing public offer using Decimal and structured datetime equality. Before recording an agreement it checks both parties' prices, pickup windows, academic pickup deadline, rental duration, and seller availability. Incompatible prices can exchange bounded counteroffers and fail at the eight-turn limit. Incompatible schedules or duration fail before an invalid proposal is shared.

An agreement enters `Agreement proposed`, then one polling advance transitions it to `Awaiting approvals` without another agent inference or turn. Both states are persisted. Buyer and seller approval flags are independently persisted. Either rejection closes the deal. Only both approvals produce `Confirmed`.

SQLite uses SQLAlchemy's `records` table with typed record kinds: student, listing, session, and negotiation. Negotiation JSON contains private preferences, public messages/offers, agreement, timestamps, and approvals. An additive, versioned compatibility migration enriches profiles and adds a unique JSON student-ID index while keeping module interfaces stable. It is not a normalized production schema.

Opaque random demo session tokens are stored server-side and issued in HttpOnly, SameSite=Lax cookies. Participants are derived from the cookie, never from a submitted approval role. A demo switch endpoint intentionally allows any persisted student profile. GET/POST /students manage public profile metadata; new profiles get UUID-based stable IDs and can both buy and sell. Listing ownership and negotiation participants are resolved from the selected session. New approval maps contain exactly the actual buyer and seller IDs. Legacy identity IDs and approval records remain intact. The UI clears cached private judge data, stale histories, and unrelated conversations when switching profiles. This is demonstration identity, not production authentication. APP_ENV=production disables all demo identities and protected operations until real auth is implemented. Judge Mode also requires ENABLE_JUDGE_MODE=true and a loopback client. Run only on 127.0.0.1.

A per-session process lock plus expected session version prevents duplicate concurrent advances. Approval writes use the same session lock. Independent sessions can progress concurrently; Ollama inference itself stays sequential. This design requires one Uvicorn worker. Multiple processes would require transactional database locking and authenticated users. The frontend polls by requesting one advance and then fetching the persisted session; updates appear per completed agent turn, not token streaming.
